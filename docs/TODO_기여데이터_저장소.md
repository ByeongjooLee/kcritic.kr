## 문제

`neo4j_api.py` 의 크라우드소싱 기여 데이터가 컨테이너 임시 디렉터리에 저장된다.

```python
CONTRIB_DIR = Path("/tmp/kcritic_contributions")   # neo4j_api.py 상단
path = CONTRIB_DIR / f"pending_{now[:10]}_{contrib_id}.json"
path.write_text(json.dumps(record, ...))
```

이로 인해 두 가지가 발생한다.

**1. 재시작마다 전량 소실**
Render 무료 티어는 유휴 시 컨테이너를 내리고 요청이 오면 새로 띄운다. `/tmp` 는 컨테이너와 함께 사라지므로 **접수된 기여가 관리자 검토 전에 없어진다.** `admin.html` 의 승인/반려 워크플로우가 빈 목록을 보게 되는 원인.

**2. 기여자 이메일이 평문으로 남음**
`Contribution.email` 은 승인 알림용으로 받는 개인정보인데 JSON 파일에 그대로 기록된다. 임시 디스크라 오히려 통제가 어렵다. 연구 사이트라도 제3자 개인정보를 받는 이상 보관 기간·파기 기준이 필요하다.

---

## 선택지

| 방안 | 장점 | 단점 |
|---|---|---|
| **A. Render 영구 디스크(Persistent Disk)** | 코드 변경 최소 — `CONTRIB_DIR` 경로만 교체 | 유료 플랜 필요. 백업은 여전히 수동 |
| **B. Neo4j 에 `Contribution` 노드로 저장** | 이미 쓰는 인프라, 백업·조회 일원화, admin API가 Cypher로 처리 | 기여 데이터가 온톨로지 그래프에 섞임 → 레이블 분리 필요. **쓰기가 생기므로 §1의 읽기 전용 규칙과 충돌** — `/ask` 용 읽기 전용 계정과 별도의 쓰기 계정을 분리해야 함 |
| **C. 외부 관리형 DB (Supabase/Postgres 무료 티어)** | 영속성·백업·행 단위 권한, 이메일 컬럼만 별도 관리 가능 | 의존성 1개 추가, 크레덴셜 1개 추가 |
| **D. GitHub Issue 로 전환** | 인프라 0, 이력 영구 보존, 검토 UI 무료 | 기여자에게 GitHub 계정 요구. 이메일은 아예 받지 않게 됨(= 개인정보 문제 소멸) |

---

## 권고

**D → C 순으로 검토.**

- **D** 는 개인정보를 아예 수집하지 않게 되어 문제를 없애 버린다. 학술 기여는 대개 공개되어도 무방하고, `contribute.html` 이 GitHub Issue 템플릿 URL 로 넘기기만 하면 서버 코드가 통째로 불필요해진다. `/contribute` · `/admin/*` · Gemini 배치 검증까지 삭제 가능 → **공격면이 크게 줄어든다.**
- 익명 기여를 꼭 받아야 한다면 **C**. 이메일은 별도 컬럼에 두고 보관 기간(예: 승인 후 30일)을 정해 파기 배치를 건다.
- **B** 는 읽기 전용 계정 정책과 충돌하므로 권하지 않는다.
